Execution model

Function call order

Solid arrows are calls made inside the action process. Dashed arrows are orchestration transitions made by a GitHub workflow. That distinction matters: the Python modules expose the decision and release commands, but they do not directly invoke one another across the outer-loop and inner-loop action boundary.

function or SDK call workflow transition fail-closed stop

Evidence is checked twice

check.monitoring() reports evidence quality. A later evaluate.policy() invocation fetches and validates again so a policy decision never trusts a previous step's stale in-memory state.

Dispatch is deliberately external

The decision output is consumed by workflow conditions. There is no direct Python call from evaluate.policy() into the inner-loop modules.

Rollback restores recorded state

Batch rollback receives the exact previous default emitted by promotion. It does not infer a target from deployment age, naming, or creation order.

Implementation

What changed

The work is split by responsibility. The outer-loop changes make autonomous decisions defensible; the inner-loop changes make the resulting batch release operations explicit, retryable, and observable.

Outer loop: evidence and decisions

Monitoring data is now treated as evidence with a contract, not just a metric map.

  • Added shared validate_monitoring_evidence() validation.
  • Checks schema version, model and deployment identity, observation time, and sample count.
  • Returns insufficient-evidence and exit code 2 when autonomous action is unsafe.
  • Requires a non-empty policy version and validates thresholds and action names.
  • Keeps every breached rule in the audit record while the first match selects the action.
  • Emits a deterministic SHA-256 decision ID for idempotent downstream dispatch.
  • Exposes evidence identity, freshness, and sample constraints through the Docker action.

Inner loop: batch release lifecycle

Named Azure ML batch deployments are now the versioned release unit.

  • Added YAML-backed creation for batch endpoints and batch deployments.
  • Added invocation of one named deployment using a pinned file, folder, or data asset.
  • Added promotion by changing the endpoint's default deployment.
  • Added rollback to an explicitly recorded prior default.
  • Centralized state mutation in set_default_deployment().
  • Added idempotency, expected-current protection, target existence checks, and read-back verification.
  • Added action inputs, environment variables, outputs, command registration, tests, and documentation.

Guardrails

Safety contracts introduced

Automatic operation is only acceptable when evidence, decisions, and deployment state each carry enough identity to detect stale or conflicting work.

01

Evidence contract

A monitoring run is usable only when all requested identity and quality checks pass.

  • aip.monitoring.schema_version=1
  • model name and version match
  • endpoint and deployment match
  • aip.observed_at is timezone-aware and fresh
  • sample_count meets the configured minimum
02

Decision contract

The policy and evidence run together produce one reproducible audit identity.

  • policy version is mandatory
  • only supported actions are accepted
  • first matching rule determines the recommendation
  • all matching rules are preserved
  • decision JSON includes evidence and deployment identity
SHA-256(experiment | evidence_run_id | policy_version)
03

Mutation contract

A default change proceeds only from the state the workflow says it observed.

  • already at target means a successful no-op
  • missing expected current default is rejected
  • unexpected current default is treated as a race
  • target deployment must exist
  • persisted state is read back and verified

Current boundary

These changes provide the safety and lifecycle primitives, not a complete production control plane. The following remain integration responsibilities:

  • A workflow must map policy outputs to retraining, data, code, or rollback jobs.
  • A GitHub concurrency group should serialize operations per batch endpoint.
  • Azure ML's SDK does not expose an ETag or If-Match precondition here, so the guard is optimistic rather than atomic.
  • Real production telemetry and a live Azure workspace are still needed for an end-to-end pilot.
  • The broad inner utility suite retains three previously known, unrelated failures.
